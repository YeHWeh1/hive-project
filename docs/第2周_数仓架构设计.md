## 二、各层职责与命名规范

| 分层 | 定位 | 表名前缀 | 数据粒度 | 生命周期 |
|---|---|---|---|---|
| ODS 贴源层 | 原样接入业务数据，保留原始文本，不做任何清洗 | `ods_` | 最细（一行一条原始记录） | 长期保留，可追溯 |
| DWD 明细层 | 清洗、标准化、维度关联，形成事实表 + 维度表 | `dwd_` / `dim_` | 明细事实 / 维度主键 | 可重跑（insert overwrite） |
| DWS 汇总层 | 按主题轻度汇总，供指标复用 | `dws_` | 日/月 + 维度组合 | 每日/每周刷新 |
| ADS 应用层 | 面向具体指标与报表，宽表化 | `ads_` | 指标级结果 | 随需求变更 |

**库命名**：统一使用 `ydsh_` 前缀（`ydsh_ods` / `ydsh_dwd` / `ydsh_dws` / `ydsh_ads`），与第 1 周保持一致。

**字段命名**：小写下划线；维度外键以 `_id` 结尾；枚举统一转为 `*_code` 并关联维表；金额一律 `decimal(12,2)`，时间戳 `yyyy-MM-dd HH:mm:ss`。

## 三、DWD 层星型模型

### 3.1 模型结构

```
                    ┌──────────────┐
                    │  dim_date    │  日期维度（1096 天）
                    └──────┬───────┘
                           │ order_date
  ┌────────────┐    ┌──────┴────────┐    ┌──────────────┐
  │  dim_user  ├────┤  fact_order   ├────┤  dim_store   │
  └────────────┘    └──────┬────────┘    └──────────────┘
                           │ order_id
                    ┌──────┴────────────┐
                    │ fact_order_item   │   （分桶表）
                    └──────┬────────────┘
                           │ product_id
                    ┌──────┴────────┐
                    │ dim_product   │
                    └───────────────┘
```

`fact_order` 为核心事实表，通过 `user_id / store_id / order_date` 关联三个维度；明细通过 `order_id` 挂到事实表，再通过 `product_id` 关联商品维度——**订单本身不含商品，商品信息只能来自明细表**，这是建模时最容易出错的地方。

### 3.2 表清单

| 表名 | 类型 | 行数 | 存储 | 说明 |
|---|---|---|---|---|
| `ydsh_dwd.dim_user` | 维度 | 1,000 | ORC | 含 `gender_code` / `member_level_code` 外键 + `region` 合并字段 |
| `ydsh_dwd.dim_product` | 维度 | 600 | ORC | 品类/品牌已去空格，状态编码化 |
| `ydsh_dwd.dim_store` | 维度 | 60 | ORC | 日期格式统一 |
| `ydsh_dwd.dim_date` | 维度 | 1,096 | ORC | 2023-01-01 ~ 2025-12-31 |
| `ydsh_dwd.fact_order` | 事实 | 15,000 | ORC + 分区 | 按 `order_month` 分区，12 个分区 |
| `ydsh_dwd.fact_order_item` | 事实 | 37,549 | ORC + 分桶 | 按 `order_id` 分 8 桶 |
| `ydsh_dwd.fact_behavior` | 事实 | 60,000 | ORC + 分区 | 按 `behavior_month` 分区，3 个分区 |

### 3.3 字段合并（子任务 3）

| 合并字段 | 来源 | 规则 | 结果 |
|---|---|---|---|
| `order_timestamp` | `order_date` + `order_time` | `concat(order_date, ' ', order_time)` | `2024-01-24 02:21:52`，格式校验 100% 合规 |
| `region` | `province` + `city` | `concat_ws('-', province, city)` | 如 `重庆市-重庆`、`陕西省-渭南`，1000 行无空值 |

说明：部署手册示例写的是从 `ods_order` 取 `province/city`，但订单表本身没有这两个字段（只有 `store_id`），只能从用户维度 `dim_user` 合并——这是手册示例的一个错误，本项目按实际表结构调整。

### 3.4 编码映射维表

枚举字段采用「脏值 → map 表 → 标准编码 → dim 表 → 中文名称」的两段式设计：

| 映射表 | 维表 | 规范值域 |
|---|---|---|
| `map_gender` | `dim_gender` | 男 / 女 / 未知 |
| `map_member_level` | `dim_member_level` | 钻石 / 金卡 / 银卡 / 普通会员 |
| `map_pay_type` | `dim_pay_type` | 支付宝 / 微信支付 / 银行卡 / 货到付款 |
| `map_channel` | `dim_channel` | 门店 / APP / 小程序 / PC官网 |
| `map_order_status` | `dim_order_status` | 待支付 / 已支付 / 已完成 / 已取消 / 退款中 |
| `map_behavior_type` | `dim_behavior_type` | 浏览 / 加购 / 收藏 / 购买 |
| `map_product_status` | `dim_product_status` | 在售 / 下架 / 缺货 |

好处：新增脏值只需往 map 表插一行，不用改 ETL 主体 SQL；事实表只存编码，展示时关联维表取中文，避免中文重复存储。

## 四、分区与分桶策略

| 表 | 策略 | 理由 |
|---|---|---|
| `fact_order` | 按 `order_month` 分区（12 个） | 查询常带月份条件（月度趋势、同比），分区裁剪能跳过 11/12 的数据 |
| `fact_order_item` | 按 `order_id` 分 8 桶 | 明细表常与事实表按 `order_id` 关联，分桶后可采用 Map Join，减少 shuffle |
| `fact_behavior` | 按 `behavior_month` 分区（3 个） | 行为数据量大（6 万行），按时间过滤最常见 |

**为什么不用按天分区**：最初尝试 `order_date` 按天分区（366 个分区），在容器内嵌 Derby 元数据库上触发 `Too many counters` 与 `Exception rolling back to savepoint`，元数据事务无法支撑一次性创建 366 个分区。改为按月分区后稳定通过，且对本项目的查询模式（按月聚合）更贴合。生产环境若换成 MySQL/PostgreSQL 元数据库，可按天分区。

## 六、设计取舍说明

1. **ODS 不动、DWD 重建**：所有清洗在 DWD 层用 `insert overwrite` 完成，ODS 保留原始脏数据，任何时候都能重跑并复现结果。
2. **异常金额置空而非删除**：保留行、置空值、加 `amount_invalid` 标记，既不丢订单，又能让下游按需排除（GMV 计算时带 `where amount_invalid = 0`）。
3. **数量异常同样保留**：`qty_invalid = 1` 标记，明细金额置空，避免影响销售汇总。
4. **未做 DWS/ADS 落地**：本周任务重点是 DWD 建模，DWS/ADS 计划第 3 周随指标需求落地，本层设计已预留命名与粒度。
