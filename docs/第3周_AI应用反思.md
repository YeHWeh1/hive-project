# 第 3 周 · AI 应用反思

> 团队：云仓五号　日期：2026-11-10
> 说明：本文记录第 3 周使用大模型（DeepSeek）完成 NL2SQL 与经营洞察过程中的真实问题、拦截记录与改进措施。

---

## 一、AI 在本周承担了什么

| 环节 | AI 的角色 | 人的角色 |
|---|---|---|
| NL2SQL | 把自然语言转成 Hive SQL | 设计 Schema 注入、写 Prompt、做白名单校验、跑测试集 |
| 经营洞察 | 基于事实清单做归因与文字组织 | 先用程序算出事实与异常日，AI 不得引入外部信息 |
| 报告撰写 | 生成结构化分析文本 | 逐条核对数字、判断因果是否成立 |

**分工原则**：AI 负责「表达与转换」，人负责「事实与判断」。

## 二、三个被验证拦下的真实问题

### 问题 1：Schema 不全 → 模型编造字段名

- **现象**：提问「各会员等级的客单价」，模型生成 `m.member_level_name`，而实际字段是 `level_name`，SQL 编译失败。
- **根因**：Schema 只注入了 6 张主表，**没有把 4 张枚举维表**（dim_member_level / dim_order_status / dim_pay_type / dim_channel）放进上下文。模型不知道字段名，只能按命名习惯猜。
- **处理**：把 4 张维表加入 Schema 抽取范围（扩大到 16 张），并在 Prompt 里显式列出「维表字段名固定，不要自己猜」。
- **结论**：**模型不会承认"我不知道字段名"**，它会编一个看起来合理的。Schema 必须完整。

### 问题 2：相对时间 → 静默查空

- **现象**：提问「广东省上个月的销售额」，模型生成 `date_format(add_months(current_date(), -1), 'yyyy-MM')`。数据只有 2024 年，`current_date()` 是 2025 年，结果为空。
- **根因**：Prompt 只说了数据范围，没禁止相对时间函数。
- **处理**：Prompt 增加硬约束「禁止使用 current_date()/now()，本月/上月一律换算为 2024 年内的具体月份」。
- **结论**：**空结果比报错更危险**——报错会被发现，查空会被误认为是"业务上确实没有"。

### 问题 3：AI 报告的"数据存疑"，其实是我们的 SQL Bug

- **现象**：AI 在洞察报告中指出「品类占比字段均为 0.00，该表口径与整体数据不一致，数据存疑」。
- **人的第一反应**：怀疑是 ETL 出错。
- **实际排查**：直接查 `ads_category_topn`，`sales_ratio` 是 **0.1495（正确）**；但查询写成 `round(100 * sales_ratio, 2)`，在 Hive 里对 **decimal 类型**做乘法后再 round，返回了 **0.00**；改成 `round(cast(sales_ratio as double) * 100, 2)` 才是 **14.95**。
- **处理**：修正洞察脚本的取数 SQL，重新生成报告；AI 这次主动加了一句「品类销售额合计与 GMV 口径不一致，本报告未据此推算占比结论」。
- **结论**：**AI 的"异常发现"有时反映的是上游取数问题**。这条最值得记录——它不是 AI 的错误，而是 AI 帮我们发现了自己的 SQL 缺陷；但如果人不回查，就会误判成"数据脏"。

## 三、AI 的局限（本周实证）

| 局限 | 具体表现 | 应对 |
|---|---|---|
| **会编造** | 猜字段名 `member_level_name`；若不做编译校验，会直接报错或查空 | 白名单 + 执行校验 + 失败回喂重试 |
| **不做因果** | 异常日只描述"高低"，明确写「现有数据不足以判断原因」 | 这是**正确行为**，Prompt 已约束禁止编造因果 |
| **依赖上游口径** | 品类明细金额 79M 与订单 GMV 36M 的差异，AI 无法自行判断哪个对 | 人在事实清单里标注口径，AI 只做表述 |
| **会中断** | 首次生成因 `max_tokens=800` 被截断在「需」字 | 调大上限至 1800，并检查结尾完整性 |
| **绝对化表述** | 本周输出未出现「必然/一定」，但需持续检查 | 在 Prompt 中要求无数据支撑的推断标注「推测」 |

## 四、关键教训

1. **给模型的是"事实清单"，不是"原始数据"。** 本周洞察的流程是：Hive 查询 → 程序算异常（z-score）→ 事实 JSON → 模型写分析。模型没有机会自己算错数，只能组织语言。
2. **Prompt 里必须写"不允许做什么"。** 只写"你是 SQL 专家"不够，要写"禁止 INSERT/UPDATE、禁止 current_date、禁止编造表名"。
3. **空结果要当失败处理。** NL2SQL 里"执行成功但 0 行"必须人工确认是业务真无数据，还是条件写错。
4. **AI 的异常提示要回查上游。** 问题 3 就是典型：AI 说"数据存疑"，实际是自己的 SQL 有 bug。**先怀疑自己的取数，再怀疑数据。**

## 五、如果重做一次，会怎么改

| 改进 | 具体做法 |
|---|---|
| Schema 先行 | 建模完成即导出完整 Schema（含维表、含示例值），作为 NL2SQL 的固定输入文件 |
| 测试集驱动 | 先写 10 个标准问题与预期结果，再调 Prompt；本周正是这样把准确率从 6/10 提到 10/10 |
| 事实与表述分离 | 所有数字由 SQL 产出并落盘（JSON），报告只允许引用 JSON 中的数字，便于逐条核对 |
| 记录 AI 的"错误" | 保留被否决/被修正的输出（如本次的字段名猜测、current_date），这些比成功案例更有教学价值 |
